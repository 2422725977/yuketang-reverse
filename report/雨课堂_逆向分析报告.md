## 2. 网络与鉴权（这是"能不能改"的天花板）

### 2.1 两套网络栈并存（observed）
1. **新层 Dio**：`rain/network/yuketang.dart`，`class YuKetang`，字段 `Dio dio`（偏移 0x8）。例：`_checkin`（asm 1062 行，RVA `0xc521fc`）构造 `{lessonId, source: 46, joinIfNotIn: true}` → `DioMixin::post("/api/v3/lesson/checkin", data)` → `dart:convert` 解 `response.data`。**魔法数 `source=46`**。
2. **旧层 BaseNet**：`xuetang_base/xuetang_base_net.dart`（5371 行），统一出口 `BaseNet::requestPost`（RVA `0x923178`）、`requestGet`、`addHeader`（RVA `0xbde930`）、`putCookieToHeader`、`setCookieToFile`、`addInterceptor`、`setProxy`、`mutileRequest`。**定位签到的提交、多数业务 POST 走这里。**

### 2.2 鉴权模型（observed，`rain/core/app.dart` 的 `_getInterceptor`）
| 方向 | 行为 |
|---|---|
| 响应拦截 | 解析响应头 `Set-Cookie`（`dart:_http` 的 `_Cookie::_parseSetCookieValue`）。cookie 名 `csrftoken` → 写静态字段 `0xd58` + `BaseNet::addHeader({X-CSRFToken: 值})` + `saveData("token", 值)`；cookie 名 `sessionid` → 写静态字段 `0xd5c` + `BaseNet::addHeader({sessionid: 值})` + `saveData("sessionid", 值)`；响应头 `Set-Auth` → 写入 config 的 `field_7b` |
| 请求拦截 | 取用户信息 `uid` → 头 `X-UID`；`config.field_7b` 非空 → 头 `Authorization = "Bearer " + token` |
| 重新登录 | 捕获 `RequestLoginEvent` → `NavigatorState::pushNamedAndRemoveUntil("/userLogin")` |

**关键结论（observed + inferred）**：拦截器里**没有**请求签名、时间戳、nonce、HMAC、参数摘要。也就是说：
- 服务端不依赖客户端签名做完整性校验（observed：无签名代码）；
- 请求体的字段伪造/重放在密码学上零门槛，**上限完全由服务端会话状态机决定**；
- 因此"改客户端判定"只在**纯本地 gate**（倒计时、范围显示、按钮可用性）有效；**"改服务端结果"必须改请求体字段，且必须实验验证服务端是否复算**（unverified，实验见 §11）。

### 3.5 客户端可篡改点（**本模块的核心结论**）
observed：服务端在 `eligibility` 里就回了 `isLate / wouldBeLate / radiusM / centerLat / centerLng / serverTime`，客户端 `_updateWouldBeLateFromClock`、`_applyRangeStateInPlace`、`_isInLateSignInWindow` 只是**结合本地时钟复算用于展示与按钮 gate**。
inferred：因此
1. **可改**：倒计时显示、"迟到"提示、按钮是否可点（本地 gate）、`forceLate` 走哪条分支 —— 改这些只影响本机 UI，服务端记录仍是它自己算的。
2. **可改但需服务端配合**：请求体 `lat/lng/address` —— 服务端据 `distance(center, latlng)` 判定是否在范围内（inferred），改坐标 = 真正的"范围外签到"注入点，其是否被复算/风控要看服务端（unverified）。

### 3.6 迟到 / 补签 / "成绩单显示成功" 的字段级证据（本轮新增，全部 observed 除标注外）

- "老师端名单"与"成绩单"读**同一份服务端签到记录**；客户端不存在"只改其中一个视图"的输入面。

**5. 分类结论（inferred，按 `apk-reverse/references/account-gates.md` 的"谁拥有这个行为"判据）**
- 绑定状态由**服务端**持有并裁决（100030/100038 是服务端响应码），客户端**没有任何本地布尔量**可以翻转来"变成已绑定"。因此 patch 客户端只能改到"提示不弹了/页面能开"，这是 account-gates 里明确点名的**半状态**（比登出更糟：UI 认为已绑定，服务端在加入班级、签到、考试时继续拒绝）。
- 客户端能做的两件真事：① 用客户端自己的写入通道 `POST /v/course_meta/edit_user_info` 提交 `school`+`school_number`（等价于不经过 H5 页面完成绑定表单提交，**能不能成功仍由服务端决定**）；② 用 `POST /school_name/school_name_query` 取学校列表/校验学校名是否在服务端学校库内。
- 客户端**做不到**：让服务端认为账号已绑；绕过学校白名单、学号唯一性/格式校验、实名与手机号门槛（这些判断的输入与结果都在服务端）。
- 因此正确说法是"**绕过客户端绑定流程**可行（直接打 API / 用 H5 页面本身），**绕过绑定本身**不可行"。

**6. 边界条件提醒（observed 文案）**：微信登录路径存在"跳过后无法再绑"的设计 —— "跳过后微信为新账号则无法绑定，是否继续?"（0xfdba4 / 0x175c52）、按钮"不绑定"（0x1333d6）；`user_status_bean` 另有 `no_bind` 字段。跳过会把你推进一个更受限的账号状态。

## 11. 对照实验协议（把上面所有 unverified 变成 observed）

原则（R2/R4）：**单变量 + 对照**；先 local 后 server；每个结论都留原始与改包两份轨迹。

1. **环境**：一台测试机装 control（原始 APK），抓包（HTTP Toolkit / mitmproxy + 用户证书；注意 `networkSecurityConfig` 与 `usesCleartextTraffic=true`，observed）。
2. **抓一次完整签到**：`/api/v3/lesson/checkin` 与定位签到 `submit`，记录服务端返回的 `isLate/checkInTime/session`。
3. **单变量实验 A（坐标）**：把 `lat/lng` 改成范围外坐标（`ykt/hooks/ykt_hooks.js` 观测 `_submit` 的实参，或代理层改写），看服务端是否回 `isLate: true` 或报错 —— 判定"服务端是否复算距离"。
4. **单变量实验 B（迟到）**：改本机时钟（不改包）看 UI 是否放行、服务端记录是否一致 —— 判定"迟到判定归属"。
5. **单变量实验 C（互评分数）**：`_submitScore` 的 `reviewScore` 改成满分，回读 `/api/v3/lesson/review/get-problem-review-detail` —— 判定服务端是否夹取/校验权重。
6. **单变量实验 D（作答）**：`/api/v3/lesson/problem/answer` 的 `result` 重放两次、`dt` 改小 —— 判定是否会记录"已答/耗时"、是否与服务端判分一致。
7. **单变量实验 E（监考）**：阻断 `/online_proctor/stu/monitor/feed/add` 的 action=24 —— 判定服务端是否有旁路兜底。
8. 每步都要留：请求原文、响应原文、UI 截图、以及 hook 日志（`ykt_hooks.js` 输出即证据）。

判定口径：E3/E4 若返回成功且 `isLate=true`，则"补签成功但老师端能看到迟到与真实时间"；若 `canSign=false` 直接拒绝，则**客户端不存在补签路径**。三条入口若要写成绩单，唯一的充分条件是服务端存下这条记录 —— 记录一旦存在，老师端与成绩单都会看到它。

**专项实验组 B0-B4（回答"能绕过身份绑定吗"）**，端点与字段见 §3.7：

| 编号 | 变量 | 操作 | 观察与判定 |
| --- | --- | --- | --- |
| B0 | 对照 | 已绑定账号正常扫码/加入班级 | 无 100030/100038，功能可用（确认这两个码就是"未绑定"的判据） |
| B1 | 账号状态 | `GET /v/course_meta/user_info` | `school`/`school_number` 是否为空 → 客户端"绑定状态"只是服务端字段的回显 |
| B2 | 学校库 | `POST /school_name/school_name_query {query}` | 学校名是否必须命中服务端学校库；不命中时绑定是否必然失败 |
| B3 | 写入通道 | `POST /v/course_meta/edit_user_info`（`school`+`school_number`，等价于"我的信息"页保存） | 是否 200；返回后 B1 是否变化 |
| B4 | 裁决点（关键） | B3 之后重新 `POST /api/v3/lesson/checkin {inviteCode,source:44,joinIfNotIn:true}` | 仍 100038 → 服务端不承认，绑定驳回；正常 → 服务端已承认绑定 |

判定口径：**只要 B4 仍回 100038/100030，任何客户端 patch（含把 toast、`Go_Bind` 弹窗、本地 gate 全关掉）都只是半状态**；反过来，若 B3+B4 直接成功，说明"绑定"这件事的判定粒度就是这两个字段，不需要绕过 —— 需要的是服务端接受的学校名与学号。

## 12. 一页速览（给不想读全文的人）

1. 雨课堂 = Flutter 外壳 + `libapp.so` 里未混淆的 Dart 业务 + 大量云侧 H5；**Java 层只有光速虚拟机检测**。
2. 鉴权是 Django 会话 cookie（`csrftoken`/`sessionid`）+ `X-CSRFToken` + `X-UID` + `Bearer`，**没有任何请求签名**。
3. 签到：普通签到与定位签到；服务端下发 `isLate/wouldBeLate/radiusM/serverTime`，客户端只做展示型本地 gate（可改 UI，改不了记录）；真正可下手的字段是 `lat/lng/address` 与 `source`。
4. 作业：**App 内没有作业逻辑**，是 H5 + OSS 直传 + `callHomeworkJS` 回调；客户端能伪造 `fileUrl/fileName/uploader`。
5. 成绩：三个写入点（`review/submit-review-score`、`problem/grade`、`problem/teacher/score-detail`）的分数与身份全是客户端参数；最终成绩单在云侧 H5。
6. 作答：`problem/answer` 的 `result/problemType/dt` 与视频题的 `answer` 完全由客户端构造，是四个模块中最直接的输入信任缺口。
7. 反作弊：光速虚拟机规则集（Titan GLES/Vulkan、isulad overlay、csaic）+ 分屏/截屏回调 + 考试监考 action 码（24/16/20，客户端驱动）。
8. 所有"能不能得逞"的答案都在 §11 的七个单变量实验里，不在反汇编里 —— 这份报告只承诺结构，不承诺绕过。
9. 签到的"迟到/缺勤/补签"：客户端**没有"补签"字样**，"迟到/缺勤"是老师端超时策略（`timeoutMode/lateAfterMs`，§3.6）；提交体里**没有时间字段**，`checkInTime` 由服务端回填 —— 想"补签且不留痕"需要的是服务端时刻与规则，客户端唯一可控字段是 `lat/lng/address` 与入口 `source`。
10. 老师端名单与成绩单读同一份服务端记录（同一接口族的 bean 字段可证：overview 带 `isLate/time/address/lat/lng`），**客户端做不到只让其中一个视图"显示成功"**；可行与不可行的边界由 §11 的 E0-E4 判定。
11. 身份绑定（学校/学号）：`100030`（扫码）/`100038`（加入班级）是**服务端业务码**，客户端只把它显示成 toast；绑定界面是两个 H5（`/v/index/bindSchool_list`、`/static/html/tsinghua_bind.html`），客户端唯一的原生写入通道是 `POST /v/course_meta/edit_user_info`（`mine/my_info_page.dart`，字段 `school/school_number/role/name/avatar/email`）。**绕过客户端流程可行，绕过服务端绑定裁决不可行**（§3.7、§11 B0-B4）。
12. 身份信息写入的信任面：`edit_user_info` 的 `school`/`role` 由客户端提交，`/school_name/school_name_query` 决定可选学校集；真正的门槛在学校白名单、学号校验、实名与手机号（`user_status_bean.no_bind/phone_status/email_status`）。
13. 会话是**可轮换的服务器状态**：客户端把 `Set-Cookie` 里的 `csrftoken/sessionid` 与响应头 `Set-Auth` 实时吸收进请求头（§2.4），cookie 一变旧请求立刻失效（业务码 100000 → 跳 `/userLogin`）——**任何重放/自动化脚本必须逐响应同步 cookie**，这是四个模块所有实验的共同前提。
14. WebSocket 握手**不带鉴权头**，身份全靠首帧 `hello`，入站帧无签名/无时间戳/不校验发送者（§2.3、`report/_board_ws.md`）；服务端是否按角色过滤 op 是 **unverified**，用 `replay/ykt_client.py ws-hello` 判。
15. 与四模块相关的命名路由只有 5 条：`/exam`（考试页）、`/webview`（**18 个云侧 H5 的唯一容器**）、`/danmu`、`/receiverJoinFree` 与 `/receiverCode`（加入课堂）；全表 28 条见 §20。
16. **"不改包接自建后端"有 4 个出口**，其中运行期可达且无域名白名单的有 2 个：deeplink `serverUrl`（processLinkParams 0xc20698）与 JS 桥 `bind_other_env`（app_js_call_flutter.dart:1503/1509）；另两个是静态位（环境位 0xd14、代理开关 0x178c/0x1788）。
17. **学习时长走客户端心跳**：`POST /mobile-app/video-log/heartbeat/`，体 `{"heart_data":[…]}`，单条 22 字段（`ts/sp/cp/tp/d/skuid/lesson_id/classroomid…`），`ts` 是客户端本地时钟、`sp` 是播放位置 —— **服务端没有独立时钟可对（对比签到族有 serverTime）**；失败数据落 `heartbeat.db` 的 `HeartBeatTable` 后补传（§21）。
18. 客户端**无"补签"概念**、无作业判分、无成绩计算：所有"时间侧/分数侧"的量都由服务端按客户端上报累加，客户端的自由度集中在"报什么"（§21 §5）而不是"改结果"。
19. **监考 action 码封闭且无第二来源**：{16,20,24,60,62,64,96} 七个码全部由客户端事件驱动，HTTP 体只有 `{exam_id,action}`（96 加 vm_report）；60/62/64 经由服务端 H5 落库（§22.1）。
20. **反作弊只打虚拟机不打注入**：光速检测规则 3 条（titan 图形栈 / titan 内核+6816 / iSulad 容器），frida/xposed/ptrace 关键字 0 命中；且 Java`schemaVersion=1` 与 Dart 要求的 2 不一致 → **action 96 不可达**（§22.4）。
21. 截屏判定是 MediaStore 启发式（第三方插件），非内核级；`cut_count` 等计数由客户端上报累加（§22.3 §22.6）。
22. **Android 端有两条互不相通的鉴权链**（§24.3）：Dart 原生走 `x-client: app` + `xtua` + `x-uid`，H5/WebView 走 `x-client: web` + `xt-agent: web` + `classroom-id` + `x-csrftoken` + `referer`。混用头是手工复现一律 401 / 50000 的唯一原因。
23. **成绩链三个 GET 全部只读且明文**（§24.5）：`assessment/sku_config/{sku}`（权重：签到 0.3、异常签到 ×0.5、习题 0.5、小测 0.2）→ `schedule/score_detail/single/{sku}/0/`（4 个 leaf 各 7.5，合计 30）→ `schedule/score_statistic/{classroom}/{sku}`（班内 max/min/avg 均 30）。
24. **签到资格端点无查询参数**（§24.4 静态 + §23 实测）：`GET /api/v3/lesson/location-checkin/eligibility` 全二进制无 `lessonId=` 字面量，服务端按"当前学生 + 当前课堂"上下文解析；签到来源（扫码/公众号/手动）由服务端记录并在课堂报告回显（§24.6），客户端无隐藏字段。
25b. **扫码只是入口，二维码里只有一个字符串**（§25.1）：19 位 lessonId 走 `POST /api/v3/lesson/checkin`（source 42），≤11 位走老接口 `POST /wxapi/lesson_check_in`；码上没有签名/时间戳/nonce，客户端也不做任何有效期判断。**过期二维码实测被服务端拒**：`{"code":50004,"msg":"LESSON_END"}`（§25.3）；`/api/lesson/web_check_in` 校验的是「课堂暗号」本身（错则 10037，§25.4）。
25c. **扫码的第一站是 `POST /api/v3/app/scan`，不是 checkin**（§26.2）：客户端把二维码原文装进 `{"url":…}` 交给服务端解析，返回 `ScanBean{type,value}` 再按 7 种 type（`checkin`/`enterlesson`/`joinclassroom`/`location_checkin_setup`/…）二次分发；二维码真伪与时效只在这一步校验。实测：URL 形状 → `51201 动态二维码不合规范`；纯码 → `50033 QR_CODE_NOT_FOUND`（服务端有二维码注册表，动态码是服务端签发的短码，客户端算不出）。
25d. **社区实现给出第二套 source 语义**（§26.1）：1 微信扫二维码 / 5 微信·小程序 / 14 PC·Web / 21 二维码 / 22 暗号 / 23 APP 点课堂；配合 `lesson_abnormal_sigin_percent 0.5`，「走异常签到拿 50%」是比伪造更现实的一条路。
26. **网关只认一个明文头**（§25.5）：`App::getInterceptor` 0x1450ddc 把 Cookie 里的 `sessionid` 复制成同名请求头下发，网关据此鉴权；补上该头后宿主直连同 IP 同 Cookie 即 `200 + code:0` —— 无签名、无设备指纹、无 IP 绑定，此前所有 401/50000 都是缺这一个头。
27. **绑定状态的权威判定在 `/pc/**` 族**（§24.7）：`register/get_user_bind_status/`、`is_bind_phone`、`force_bind_status?classroom_id=...`；Dart 侧 `UserStatusBean.no_bind` 无人引用，与"进课时由服务端强制"一致。

## 24. 实测抓包与字段级验证（2026-11-16，自有 AVD `cx30` / Android 11）

### 24.1 为什么放弃 Frida 改走网络层

本机 arm64 模拟器（ranchu，`/proc/cpuinfo` CPU part `0x000`）上 Frida 的 inline hook **写入了补丁但不产生回调**，逐条排除后判定为环境问题，不是脚本问题：

| 检查 | 结果 | 结论 |
|---|---|---|
| `Interceptor.attach(base+0x86ec18)` 返回值 | 成功 | 挂载 API 正常 |
| 挂载后读该地址首 4 字节 | `fd79bfa9` → `fa601e16` | 跳转确实被写入 |
| 挂 `libc.so` 的 `clock_gettime` / `nanosleep` / `gettimeofday` / `malloc`（地址 `0x7a888ec64c` 等）后反复切页 | **零回调**，App 不崩不卡 | 回调分发层不工作 |
| 加载期用 `new File(path,'a')` 写 `/data/data/com.xuetangx.ykt/files/hit.log` | 成功 | 排除文件写入受限 |
| `/proc/PID/maps` 中 `libapp.so` 基址 | 唯一 `0x7775d8d000`，offset 0 `r--p`、`0x760000` 起 `r-xp` | 与静态 `vaddr=0x760000` 一致，base+RVA 成立 |

结论（observed）：本环境下 **所有 Frida 探针的 75 个挂点虽能通过 guard 校验、但运行时不会触发**，因此探针只能用于静态自检（`tools/guard_audit.py` 已 75/75 通过），真实请求观测必须换通道 → 采用 mitmproxy 反向代理 + 系统 CA。

### 24.2 抓包装置（可复现）

1. 代理端（宿主）：`mitmdump -p 8888 --mode reverse:https://www.yuketang.cn -w /tmp/mitm/flows.mitm --set flow_detail=1`
2. 设备信任 CA：`openssl x509 -in ~/.mitmproxy/mitmproxy-ca-cert.pem -subject_hash_old -noout` → `c8750f0d`；`adb root && adb remount` 后 push 为 `/system/etc/security/cacerts/c8750f0d.0`（644 / root:root / `restorecon`），重启生效。App 无证书锁定（§17.2 已证），故系统 CA 即足够。
3. 引流（设备内，root）：`iptables -t nat -A OUTPUT -p tcp -d 198.18.2.97 --dport 443 -j DNAT --to-destination 10.0.2.2:8888`（`198.18.2.97` 为宿主 `dig +short www.yuketang.cn` 的 fake-ip，guest `wlan0` 为 `10.0.2.16/24`）
4. 解析：`python3 tools/mitm_dump.py live/flowsN.mitm live/captureN` → 每条流导出 `NNN_<safe>.req.txt` / `.res.txt`（含完整请求头、JSON 正文 20KB）与 `index.tsv`
5. 收尾：`iptables -t nat -D OUTPUT ...` 撤销 DNAT、删除 `/system/etc/security/cacerts/c8750f0d.0`

## 25. 扫码 / 动态码 / 过期二维码签到的实测结论

> 本章全部基于**自有测试号 + 自有 AVD** 的受控实验（2026-11-16 21:00–21:10），请求逐条落盘在 `live/replay/`。
> 标注：observed = 抓包或实测看到；inferred = 由代码/响应形状推出；unverified = 未证。

### 25.1 二维码里到底装了什么（observed，静态）

扫码页的分发器在 `rain/home/scan_related/hms_scan_page.dart` 0xccb2ec–0xccb3a0：

| 步骤 | 指令 | 含义 |
|---|---|---|
| 取解析结果 | `ldur w3,[x0,#0x23]` | `state.field_23` = 扫码解析出的对象 |
| 比对类型 | `Object::==` 与字面量 `"checkin"`（`[pp+0x66598]`，全树唯一） | 只有 type 恰好等于 checkin 才走签到 |
| 取码值 | `field_b`（String）→ `field_7` → `LoadInt32Instr` → `cmp x2,#0xb` `b.le` | `field_7` 是 String 的**长度**（Smi 右移 1 位解码），**长度 ≤ 11 走老接口** |
| 长度 > 11 | `bl 0xcd042c` `_postLessonCheckin` | POST `/api/v3/lesson/checkin`，body `{source:42, lessonId:<码值>, joinIfNotIn:true}` |
| 长度 ≤ 11 | `bl 0xccf278` `_postOldLesson` | POST `/wxapi/lesson_check_in`，body 键 `lesson_id/source/action/userid` 等 |

由此得到三条硬结论：

1. **二维码只承载一个字符串**（19 位 lessonId，或 ≤11 位的旧课/暗号码），没有签名、没有时间戳、没有 nonce。
2. **客户端不做任何有效期判断**：全二进制里 `过期` 只命中订单/兑换码文案，二维码相关中文只有「未正确识别二维码」「请对准二维码」「未扫描到二维码」。
3. 因此「扫码」与「拿到 lessonId 直接发请求」在客户端完全等价——扫码只是入口。

### 25.5 机制侧记：为什么之前所有宿主重放都是 401 / 50000（observed，本章最重要的发现）

`App::getInterceptor`（RVA 0x1450ddc，`rain/core/app.dart`）在响应 `set-cookie` 里命中 `sessionid` 时：

```
0x1451098  "sessionid" 比较
0x14510d0  StoreStaticField(0xd5c)   ; 缓存 sessionid
0x14510e0  AllocateArray(4) + 填 {"sessionid": <值>}   ; 造表
0x1451130~ addHeader(...)            ; 下发给后续所有请求
```

也就是说 **App 把 sessionid 从 Cookie 里复制成一个同名明文请求头**。网关（envoy + 业务服务）认的是这个头：

- 缺这个头：`/api/v3/**` → `HTTP 401`（空体）或 `{"code":50000,"msg":"UNAUTHENTICATED"}`
- 补上这个头：同一台宿主、同一个 IP、同样的 Cookie → `200 + {"code":0,"msg":"OK"}`

**推论（observed）**：不存在设备指纹、签名或 IP 绑定；此前 §24.10 记的「宿主 401 原因未证实」到此闭合。也说明这一步"鉴权"只是把 Cookie 值抄进头里，**没有任何密码学保护**——这是本 App 全链最容易复现的一环。

### 25.6 判定表：能绕 / 不能绕

| 目标 | 客户端有没有可改的判断 | 服务端有没有独立判定 | 结论 |
|---|---|---|---|
| 用当前有效的动态码/暗号签到 | 只转发码值 | 有（暗号有效性、lesson 状态） | **可以**，只要码有效；码按课堂轮换，过期即失效 |
| 用过期二维码（旧 lessonId）签到 | 无任何时间判断 | 有（LESSON_END 50004） | **不行**，实测被拒 |
| 用别人的/猜的 lessonId 签到 | 无 | 有（是否在课堂、joinIfNotIn、教师限制） | **不行**，返回 10030/10038 类业务码 |
| 定位签到时改位置/改迟到 | 无时间字段可改 | 有（服务端时钟 + radiusM + lateAfterMs + wouldBeLate） | **不行**；改客户端只会让 canSign=false 时仍发请求，服务端照旧拒 |
| 改签到结果（事后补签） | 无此功能 | 无客户端端点（`checkin/revise` 等只在云侧） | **不行**，客户端整条链不存在 |
| 隐藏签到来源（扫码/公众号/手动） | 无字段 | 有（课堂记录里直接展示） | **不行** |

### 26.2 三个直接改写我们结论的点

**(1) 我们漏掉了客户端真正的"扫码入口"——`POST /api/v3/app/scan`（observed，静默）**

`_HmsScanPageState::scan`（0xccab40，`hms_scan_page.dart`）在拿到扫码枪/相机文本后，**第一步不是直接发 checkin**，而是：

```
0xccac24  {"url": <二维码原文>}          ; 只装一个键
0xccac58  AllocateScanBeanStub (size 0x28)
0xccacac  "/api/v3/app/scan"
0xccacdc  bl BaseNet::requestPost
```

服务端解析后返回 `ScanBean{type, value}`，客户端再按 `type` 二次分发（0xccb024 闭包里的比较串）：`app_web_login` / `pauseScan` / **`checkin`** / **`enterlesson`** / `joinclassroom` / `location_checkin_setup` / `locationCheckinMobileSetup`。

**含义**：二维码原文（含动态码）的**真伪判定发生在 `app/scan`，不在 `lesson/checkin`**。这解释了为什么我们直接打 checkin 只得到 `LESSON_END`——那条路根本不校验二维码本身的签名/时效，只校验 lesson 状态。

**(2) 动态二维码是服务端的"随机码 + 注册表"，不是客户端能算的东西（observed，实测三次）**

对 `POST /api/v3/app/scan` 做格式探针（每次一个变量）：

| 传入 `url` 值 | 响应 |
|---|---|
| `https://www.yuketang.cn/lesson/fullscreen/v3/1820276486008339584` | `{"code":51201,"msg":"动态二维码不合规范","data":{"type":"default","value":""}}` |
| `https://www.yuketang.cn/m/v2/lesson/student/1820276486008339584` | 同上 51201 |
| `1820276486008339584`（纯码） | `{"code":50033,"msg":"QR_CODE_NOT_FOUND","data":{}}` |
| `checkin://1820276486008339584` | 同上 50033 |

两条判读（inferred，但证据很强）：
- **51201** = 形状不对（服务端期待一个短码，不是 URL）；
- **50033 QR_CODE_NOT_FOUND** = 形状对，但**服务端二维码注册表里没有这个码** → 动态二维码是服务端签发并存储的**短随机码**（带 TTL），客户端既算不出也猜不到（除非码空间很小，未验证）。
- 这同时证实社区那句"暂无法支持动态二维码"的根因：**它不是技术难度，是没有服务端签发的码**。

**(3) 存在第二套 source 语义，且服务的不是同一个环节**

| 来源 | source 值 |
|---|---|
| 我们的 1.3.6 客户端（observed，asm 常量） | 42 扫码 / 44 手输数字码 / 46 通用封装 / 54 定位签到 |
| 社区（PC/Web/小程序/暗号，linfish330） | 1 微信扫二维码 / 5 微信·小程序 / 14 PC·Web / 21 二维码 / 22 暗号 / 23 APP 点课堂 |

两者不冲突：**source 是"我从哪个入口进来的"标签，不是权限**。但它是**唯一一个既能改又可能影响计分的字段**（配合 §24.5 的 `lesson_abnormal_sigin_percent 0.5`：服务端有"异常签到只给 50% 分"的分支）。→ 见 §26.4 路径 B。

### 26.3 本轮实测：社区端点在我们的部署上能不能用

| 端点 | HTTP | 响应 | 结论 |
|---|---|---|---|
| `GET /api/v3/classroom/on-lesson` | 200 | `{"code":0,"msg":"OK","data":{"onLessonClassrooms":[]}}` | **可用**。这是"不扫码找进行中课堂"的正门（比 `on-lesson-upcoming-exam` 更贴切） |
| `GET /api/v3/classroom/drop-down` | 200 | `{"code":0,"msg":"OK","data":{"courses":[]}}` | 可用（需参数才有内容） |
| `GET /api/v3/connection/get-token` | **404** | `Resource not found` | 该路径属其它部署（长江/荷塘），www 上不存在 |
| `GET /api/v3/lesson/basic-info?lessonId=…` | **401** | 空体 | **lesson 级资源需要额外凭证（lessonToken / Bearer）**，与签到端点不同 |
| `GET /api/v3/lesson/get-invitation?lessonId=…` | **401** | 空体 | 同上 —— 邀请码不能白拿 |
| `GET /api/v3/lesson/fetch-dynamic-invitation?lessonId=…&v=2` | **401** | 空体 | 同上 —— **动态邀请不能由学生侧拉取** |
| `POST /api/v3/app/scan` ×4 | 200 | 51201 / 50033 | 见 §26.2 |

对照意义：**签到端点（`lesson/checkin`）是全链唯一"不要 lessonToken 就能打"的写接口**，这既是它脆弱的地方，也说明服务端把校验全部压在 lesson 状态 + 二维码注册表上。

### 26.4 转换后的五条路径（按现实可行性排序）

**A. 转发二维码原文（唯一无需伪造、且真的可行的一条）**
二维码 = 一段可直接复制的文本；`app/scan` 只吃这段文本，不看设备、不看地理（定位签到才看坐标）。所以：**二维码文本/截图可以在有效期内转发给同班任何人，谁先扫到谁签上**。这不是绕过，是这条链的固有性质——服务端认为"拿到码 = 在场"。要做"代签"，只需把码转发出去；反过来，防代签的唯一手段是老师改用**定位签到**（§3.5：`lat/lng/radiusM` + 服务端时钟）。

**B. 主动走"异常签到"分支拿 50%（最被忽视的一条）**
`sku_config` 里有两个开关：`lesson_abnormal_sigin_percent = 0.5`、`lesson_get_checkin_score_when_checkin_exception = 0`。意思是：**签到被判定为"异常"时按 50% 计分，而不是 0**。迟到/超时/未在范围内都属于这一类。所以"补签"的现实替代品不是伪造，而是**让签到落在 exception 分支**（例如超时后仍提交、或老师把 `timeoutMode` 设为 markAsLate）——分少一半，但记录是真的，不会被判违规。**可测**：E 组场景里把 `source` 与提交时刻错开，看成绩单 leaf 的 `user_score` 是否变 3.75（7.5×0.5）。

**C. 不扫码的"找课 + 签到"（社区主流做法，我们实测门是开的）**
`GET /api/v3/classroom/on-lesson` 返回进行中课堂 → 取 lessonId → `POST /api/v3/lesson/checkin {lessonId, source, joinIfNotIn:true}`。整条链不需要二维码、不需要 `app/scan`。**只要 lesson 未结束，这条就能签上**（这也正是市面所有"自动签到"脚本的骨架）。代价：source 会显示成你选的入口（不能隐藏，§24.6）。

**D. 换客户端面（未测，最值得下一步做）**
小程序（source 5）/ PC Web（source 14）是**与 App 完全不同的鉴权面**：小程序包（`.wxapkg`）可直接反编译，PC 端是纯 HTTP + cookie（就是我们一直在用的那条会话）。App 端没有的能力（比如拉二维码、看邀请）在 PC 端可能只是"登录了就能看"——**`fetch-dynamic-invitation` 在 App 里 401，不代表在 PC 会话里也 401**。这是本轮唯一没打的、且成本最低的新面。

**E. 动态码本身：伪造不可行，枚举存疑（未验证）**
要签上动态码，必须有服务端签发的短码。除非码空间极小（如 6 位纯数字）且服务端不做频控，否则不可枚举。**不建议实测**：这属于对 `app/scan` 的批量请求，最容易被风控标记的一条路。

### 26.5 判定表（更新 §25.6）

| 目标 | 结论 | 依据 |
|---|---|---|
| 过期二维码签到 | 不行 | `LESSON_END`（§25.3）；`app/scan` 还会额外给 `QR_CODE_NOT_FOUND`（§26.2） |
| 伪造动态码 | 不行 | 服务端注册表 + 51201/50033 双错误码 |
| **转发有效码代签** | **可以** | 码是纯文本，`app/scan` 不校验设备/地理 |
| 不扫码、直接对进行中课堂签到 | **可以** | `on-lesson` → `lesson/checkin`（§26.3） |
| 拿 50% 的"异常签到" | **可以（需老师侧策略配合）** | `lesson_abnormal_sigin_percent 0.5` |
| 事后改签到结果 | 不行 | 客户端无端点；改签在云侧 |
| 隐藏签到来源 | 不行 | 服务端记录并回显（§24.6） |

## §28 开课前的深挖：签到的推送面、自动化的边界、以及可对照的基线

> 背景：用户准备「等下开课堂」（m02621）。本节把开课瞬间会发生什么、哪些环节客户端能自动、哪些必须人手点，逐条钉死，并留下**可在课后直接对照的基线快照**。

### 28.1 新事实一：普通扫码签到**没有** WS 推送

`rain/websocket/processer/` 两个分发器（学生侧 `receiver_processer.dart` 86 个 op 字面量、教师侧 `remote_control_processer.dart`）全量枚举后：

```
grep -oE '"[a-zA-Z_0-9]*checkin[a-zA-Z_0-9]*"' receiver_processer.dart
  → "locationcheckinext"  ×2
    "locationcheckinend"  ×2
remote_control_processer.dart  → 同上（两项）
```

**没有任何 `checkin` op**。含义：老师点「签到」开普通扫码签到时，学生端**收不到 WS 推送**。但这不等于「没有通知通道」—— 见 §28.8：**只要进入课堂页，页面自己就会提交签到**。所以普通签到的真实语义是「进没进这个课堂页」，而不是「扫没扫码」。

定位签到则相反：`locationcheckinext`（开/续期）、`locationcheckinend`（结束）双 op 齐全，是唯一有推送的签到形态。

### 28.2 新事实二：定位签到会自动弹页面，但**提交仍然只能人手点**

推送到达后的完整链路（observed，逐指令）：

```
WS locationcheckinext
  → _applyLocationSignNotification  (0xbd7ac4)
      setState(...)                     // 0xbd7bf8
      _maybeAutoOpenLocationCheckIn     // 0xbd7c0c
      _Timer::cancel                    // 0xbd7c28  取消上一轮倒计时
      Timer.periodic(Duration@11e3121)  // 0xbd7c64  起新的刷新/倒计时
```

`_maybeAutoOpenLocationCheckIn`（0xbd7ca4，size 0x19c）三道门：

| 门 | 位置 | 含义 |
|---|---|---|
| ① `field_0x163` 已置真则直接 return | 0xbd7ce4 / 0xbd7d38 | **同一节课只自动弹一次**，弹过就不再打扰 |
| ② 入参类型必须 == `Instance_LocationSignInState` | 0xbd7d1c | 只有定位签到会走这里 |
| ③ `LoadStaticField(0xdf4)` 必须为真 | 0xbd7cf4 | 全局自动弹窗开关 |

三门全过 → `blr` 到匿名闭包（0xbd7e40）打开 `location_check_in_page`。

**但提交动作没有任何自动路径**：`_LocationCheckInPageState::_submit`（0xdee0b0）在全 asm 里只有**一处** `bl` 调用 —— `0xdee098`，其调用者是按钮的 onPressed 闭包（0xdee078，建于 0xdedc70）。也就是说页面自动弹出来之后，**仍然要手指点一下「签到」**。

### 28.8 关键发现：进入课堂页就会**自动签到**（这才是「不扫码」的正解）

`_ReceiverClassPageState::initState`（RVA 0xbd51b0，size 0x748）的调用序列（observed，逐指令）：

```
0xbd52d8  collectEventLog({app_jpush_route, receiver_class_page})
0xbd52fc  App::_getInstance().field_3f = true            // 置「在上课」标志
0xbd5330  App.field_4b = this.widget.field_b             // 存 lessonId
0xbd5358  StoreStaticField(0xdf4, this.widget.field_f)   // 存入口来源/自动弹窗门禁
0xbd5364  _getAuditorStudentRecord()
0xbd536c  _getLiveRecord()
0xbd5374  _applyStatusBarStyle()
0xbd537c  _postLessonCheckin()          ← ★ 无条件调用，没有 if 包裹
0xbd5384  _connectSocket()
0xbd538c  _loadCourseAllTypes()
```

`_postLessonCheckin`（RVA 0xc196cc，size 0x164）开头没有任何守卫条件，直接构造并发出：

```
0xc19734  "source"       ← this.widget.field_f   （int，BoxInt64 装箱）
0xc1976c  "lessonId"     ← this.widget.field_b   （String）
0xc19784  "joinIfNotIn"  ← true
0xc197ec  "/api/v3/lesson/checkin"
0xc19810  bl BaseNet::requestPost
```

**结论（observed）**：进入课堂页 = 自动签到。`source` 不是常量，而是**打开这个页面时由入口传进来的 int**（公众号推送 / 学习日志 / 课程列表各传各的）。这与界面记录完全吻合：

> 课堂记录页显示「**已签到** · **20:16 通过公众号「正在上课」提示进入课堂**」

也就是说，那条「通过公众号提示进入课堂」不是签到方式的一种描述，而是**签到的成因本身**：点推送 → 打开课堂页 → initState 自动 POST checkin（source=公众号入口）→ 服务端记一条签到。

由此可以对「不扫码能否签到」给出最终答案：

| 场景 | 是否需要扫码 | 机制 |
|---|---|---|
| 有公众号/服务号「正在上课」推送 | **不需要** | 点推送 → 课堂页 → 自动 checkin |
| 无推送，但有课程页学习日志 | **不需要** | 学习日志点该节课 → 课堂页 → 自动 checkin |
| 在课堂里等老师开签到 | **不需要（若只是要「到场」记录）** | 页面已在，checkin 已发过；后续签到由服务端按签到活动再判 |
| 只在教室外面，没打开过 App | 需要（或转发二维码） | 无任何客户端路径能替代「打开课堂页」 |

**唯一真正的门槛是「打开课堂页」这个动作本身**，不是二维码。二维码只是把 lessonId 告诉你的一个媒介；而 lessonId 在学习日志/课堂列表里本来就明示。

## §29 随机点名（rollcall）能不能躲开

### 29.1 这是**教师端专属**功能（observed）

`rain/remote_control/page/more/random_naming_page.dart` 与 `bean/wss_naming_bean.dart` 构成全部实现，学生侧没有对应页面。

WS op 家族（字面量均在 asm 中观察到）：

| op | 方向 | 含义 |
|---|---|---|
| `call` | 教师→服务端 | 开始点名（请求抽一个人） |
| `callpause` | 教师→服务端 | 暂停滚动 |
| `callstart` / `callstarted` | 服务端→教师 | 开始/选中结果 |
| `calledlist` | 服务端→教师 | 已点名过的名单 |
| `callwakeup` / `callwokeup` | 服务端↔教师 | 唤醒（继续） |
| `callpaused` | 服务端→两侧 | 已暂停（学生侧 `receiver_processer.dart` 唯一命中的 call 系 op） |
| `rollcall` | 服务端→教师 | `remote_control_processer.dart:1070`（0x143abdc）分发 |

`WssNamingBean`（FromJson RVA 0x143ed54, size 0x554）字段：`op`（0x143ed78）、`uid`（0x143eebc）、`name`（0x143ef30）、`avatar`（0x143f008）、`type`（0x143f2e0）、`dt`（0x143f0e4）。教师端 UI 文案：`toBeNaming`（待点名）、`rolling`/`keepRolling`（滚动中/继续滚动）、`randomRolling`（随机滚动）、`itIsHe`（就是他）、`of`（“3 / 20”）。

### 29.2 点名池 = **已签到名单**（observed）

`_RandomNamingPageState::getParticipantList`（RVA 0xd4ce58）→ `0xd4cea4 bl YuKetang::fetchCheckinList`（0xc5687c）→ **`GET /api/v3/lesson/checkin-list`**。同页另一路 `_requestLessonDetail`（0xd4d2a0）→ `YuKetang::v3LessonDetail`（0xc5047c）只取课程元信息。

两条空态文案各自对应一种池空（`messages_zh_CN.dart`）：

- `0x8ad980`「当前课堂没有学生，不能点名」
- `0x8ad9d4`「当前课堂没有学生签到，不能点名」

→ 抽取对象是**服务端持有的签到名单**，客户端只负责滚动动画与展示。

### 29.3 抽取发生在服务端，客户端没有“参不参与”的开关（observed + inferred）

- 客户端所有 call 系函数都是**消息构造器**（`ws_connector.dart` 中 `_ callstart()` 0x1099464、`_ calledlist()` 0xd4cca0、`_ callwakeup()` 0xd4cd90 等），不含任何本地随机数抽样；`rain/util/random_util.dart` 只有 `RandomUtil::randomNumber()`（0xbd37c8, size 0x40，生成随机数字串做 URL 去缓存参数），被 edit_course_page / hms_scan_page / teach_lesson_list_page / learn_lesson_list_page / announce_detail_page 等调用，**点名页一次都没调用**。
- `random_naming_page` 的三个订阅 `_namedCountSubscription` / `_namedListSubscription` / `_namingPausedSubscription` 全部被动接收服务端推送。
- 页面里没有“只点已签到 / 点全部”的开关字面量，两种空态文案只是对不同后端返回的兜底提示 → 池由服务端决定（inferred）。

### 29.4 学生设备上**没有**“你被点名了”的提示（observed）

`receiver_processer.dart` 的 86 个 op 里，call 系只命中 `callpaused`（暂停动画用），没有 `callstart`/`callstarted`/`calledlist`/`rollcall`；全 asm 的「点名」相关中文只出现在教师端 l10n（`radomrollcall`、`toBeNaming`、`当前课堂没有学生签到，不能点名` 等），学生侧没有任何被点名弹窗文案。

→ 被点到只体现在**老师屏幕上**，学生端不弹窗、不提醒。这意味着「躲开点名」在客户端层面本来就没有可操作的界面面。

### 29.5 能不能躲：判定表

| 手段 | 是否有效 | 依据 |
|---|---|---|
| **不进入课堂页 / 不签到** | 有效（若池=已签到） | 池取自 `checkin-list`；不进课堂页就没有签到记录 → 不在名单里。代价：该节课堂分 0（§28.3 已证课堂分只看签到） |
| 迟到签到 / 异常签到 | **无效** | `isLate` 只是名单里的一个标记字段，名单仍包含你 |
| 改昵称/头像、换设备 | 无效 | `WssNamingBean` 回传的是服务端身份记录 |
| 客户端 hook 拦弹窗 | 无效（也无弹窗可拦） | 学生端无此 UI；抽取在服务端 |
| 让签到请求失败 | 有效但等价于缺勤 | 失败即无记录 → 池里没有你 |
| 退课/换号 | 有效 | 不在班级成员/签到名单内 |

**结论**：签到与“进入点名池”是同一件事的两面。想拿课堂分（=签到成功）就必然进池；想出池只能不签到。客户端不存在“签到了但不参与抽取”的状态位 —— 这并不是被拦住了，而是这个状态在协议里根本不存在。

### 29.6 与「进课堂页自动签到」的冲突

§28.8 已证：打开课堂页 → `initState` 无条件 POST `/api/v3/lesson/checkin`。所以**进课堂页 = 既拿课堂分又进点名池**，两个结果绑定在同一个动作上，App 里没有任何分离它们的路径。

### 29.7 局限

- 服务端抽样算法（是否真随机、是否排除已点名者、是否加权）不可见，标 unknown。
- 「池 = 已签到」由 `fetchCheckinList` 调用点 + 两条空态文案推断，未做教师号实测（需要教师账号开课）。

## §30 新建课程/班级做自测：学生号也能建，且建完就是该班教师

### 30.1 结论（observed）

用 `xi`（`user_id 100254372`，`/v/course_meta/user_info` 里 `role=2`）这个**学生号**，通过 `POST /v/course_meta/create_course` 成功创建了课程与班级：

```json
  "classrooms":[{"classroom_id":33843601,"classroom_name":"tstclass","role":1,"students_count":0}]}],
```

`role: 1` 即在该班级内是**教师身份**。→ 客户端与服务端都不拦学生建课，建完自动成为授课教师。

### 30.2 真实 schema（由四轮错误信息反推，全部 observed）

| 提交体 | 服务端返回 | 说明 |
|---|---|---|
| `{"course":{...},"classes":[]}` | 500 `list indices must be integers, not str` | `classes` 必须按名字取键，说明它得是 dict 不是 list |
| `{"classes":[{"add":"tstclass"}]}` | 同上 | 同上 |
| `{"classes":{"add":["tstclass"]}}` | 500 `delete` | dict 需要 `add`/`delete`/`edit` 三个键齐全 |
| `{"classes":{"add":["tstclass"],"delete":[],"edit":[]}}` | 500 `string indices must be integers` | `add` 的元素必须是对象 |
| `{"classes":{"add":[{"name":"tstclass","id":""}],"delete":[],"edit":[]}}` | **200 success** | 正确形状 |

即 `POST /v/course_meta/create_course`，header 需 `x-csrftoken`，body：

```json
{
  "course": {"name": "<COURSE_NAME>", "id": ""},
  "classes": {
    "add":    [{"name": "<CLASS_NAME>", "id": ""}],
    "delete": [],
    "edit":   []
  }
}
```

单建班级（已有课程时）：`POST /v/course_meta/v2/classroom/create`，body `{"course_id": <ID>, "classroom_name": "<NAME>"}`（`rain/home/course/create_classroom_page.dart` `save()` RVA 0xf90c90，成功回调 `TopCourseBean` + `EventBus.fire(CourseRefreshEvent)`，失败 toast `CreateFailClass`）。

### 31.2 二维码原文与邀请码（关键）

`GET /api/v3/lesson/detail` 的 `data.invitation`：

```json
{"qrContent":"http://weixin.qq.com/q/02JJAEFT7jds11R-QY1GcH",
 "qrImage":"https://mp.weixin.qq.com/cgi-bin/showqrcode?ticket=gQH48DwAAAAAAAAAAS5odHRwOi8vd2VpeGluLnFxLmNvbS9xLzAySkpBRUZUN2pkczExUi1RWTFHY0gAAgT_IvtqAwSAUQEA",
 "inviteCode":"6UZU5"}
```

两点纠正此前推断：

1. **二维码原文不是 lesson URL，而是 `http://weixin.qq.com/q/<id>` 这种微信跳转链接**。这解释了 §26 里用 `https://www.yuketang.cn/lesson/fullscreen/v3/<id>` 去打 `app/scan` 为什么回 `51201 动态二维码不合规范` —— 形状不对。
2. **`inviteCode` 是 5 位短码（`6UZU5`）**，不是长数字，所以扫码分发器里 `长度 > 11 → /api/v3/lesson/checkin`、`长度 ≤ 11 → /wxapi/lesson_check_in` 的判定，对「邀请码」走的是旧端点（§25 已记；旧端点对本部署的码无效，见 31.4）。

### 31.3 二维码原文直投 `app/scan`：成功（A 路径实测通过）

```
POST /api/v3/app/scan
body {"url":"http://weixin.qq.com/q/02JJAEFT7jds11R-QY1GcH"}
→ {"code":0,"msg":"OK","data":{"flow":"normal","type":"checkin","value":"1820383219510814976"}}
```

- 服务端把二维码原文映射成 `type: checkin` + `value: <lessonId>`，客户端拿到后走 `source=42` 的 `POST /api/v3/lesson/checkin`。
- **二维码内容对设备、地理位置、App 版本都无校验**：它只是一个服务端注册表键。
- `flow` 字段首次出现，值 `normal`（其他取值未枚举，unknown）。

### 31.4 三种签到入口的实测对照（同一课堂，全部 200）

| 入口 | 请求 | 结果 |
|---|---|---|
| 扫码（source=42） | `POST /api/v3/lesson/checkin` `{lessonId, source:42, joinIfNotIn:true}` | `code 0`，`role 1`，回 `lessonToken` |
| 换 source（21） | 同上 `source:21` | `code 0`，**与 42 逐字段相同** |
| 暗号/邀请码（source=22） | `POST /api/v3/lesson/checkin` `{inviteCode: 6UZU5, source:22, joinIfNotIn:true}` | `code 0`，**不带 lessonId 也能签到**，响应回填 `lessonId` |
| 旧版 web 签到 | `POST /api/lesson/web_check_in` `{invite_code: 6UZU5, source:46}` | `{"code":10037,"msg":"课堂暗号输入错误，请重新输入或扫码加入。"}` |

三条硬结论：

1. **`source` 不参与任何校验**：只影响服务端记录的“签到方式”展示（课堂记录页那句「通过公众号‘正在上课’提示进入课堂」就是它）。伪造 source 不会让人看起来像扫码进来的，只会在记录里留下没做过的入口。
2. **`inviteCode` 是独立可用凭证**：5 位码 + 会话即可签到一个进行中的课堂，不需要二维码、不需要 lessonId、不需要摄像头 —— 这是「不扫码签到」的第二条真路径（第一条是转发二维码原文 → `app/scan`）。
3. `10037 课堂暗号输入错误` 说明 `web_check_in` 走的是**另一套码空间**（旧版轻课堂），本部署的新邀请码在那里查不到。

### 31.5 过期判定：二维码不失效，课结束才拦（「过期二维码」的真正答案）

`POST /api/v3/lesson/end` `{lessonId}` → `{"code":0,"msg":"OK","data":{}}`，随后同一批请求重放：

| 请求 | 结果 |
|---|---|
| `POST /api/v3/app/scan` 同一 `qrContent` | **仍然 `code 0`，`type checkin`，`value 1820383219510814976`** |
| `POST /api/v3/lesson/checkin` `{lessonId, source:42}` | `{"code":50004,"msg":"LESSON_END"}` |
| `POST /api/v3/lesson/checkin` `{inviteCode: 6UZU5, source:22}` | `{"code":50070,"msg":"LESSON_END_JOIN","data":{"lesson_id":"1820383219510814976","classroom_id":33843601,"activity_id":59442599,"is_teacher":true}}` |

结论：

- **二维码/邀请码本身没有 TTL，也不存在“过期码”这个状态** —— 课后 `app/scan` 仍然解析成功。所谓“过期”完全由 **lesson 状态**（`LESSON_END` / `LESSON_END_JOIN`）表达；客户端字符串池里没有任何二维码有效期文案（§25 已核）。
- 两条路径拒绝码不同：`lessonId` 直投回 `50004 LESSON_END`；`inviteCode` 回 `50070 LESSON_END_JOIN` 并**把 classroom_id / activity_id / is_teacher 一起回给你**（信息面：短码可反查课堂与活动 id）。
- 因此「过期二维码签到」在协议层做不到：能变的只有 lesson 状态，它由教师端 `end` 决定，客户端没有本地伪造面。

### 31.6 `authorization: Bearer <token>` 确实存在（纠正 §25/§27 的否定结论）

抓包里教师端原生 `/api/v3` 请求头含：

```
authorization: Bearer <TOKEN>
sessionid: <SESSION>      ← 网关硬要求（§24 已记）
x-uid / xtua / xtbz / version / buildnumber / isphysicaldevice / brand / systemversion / incremental / uuid
```

- 之前 `lesson/basic-info`、`lesson/detail`、`fetch-dynamic-invitation` 全部 401 的原因就是这个 `authorization` 头（`lessonToken` 形态的 Bearer），不是“设备上下文”。
- 静态侧此前 grep `authorization|Bearer` 在 asm 里 0 命中，是因为该头由 web/TLS 层或原生插件拼装，不在 Dart 字面量池（具体拼装点 unverified）。

## §32 只有学生号时的签到作战面（四类签到 × 三条材料 × 硬限制）

### 32.1 学生侧只有四类签到，判定依据都在服务端

| 类型 | 服务端判定依据 | 学生侧需要的材料 | 可行性 |
|---|---|---|---|
| 普通签到 | lesson `start ≤ now ≤ end` | `lessonId` 或 `inviteCode` | 可 |
| 暗号签到 | 5 位 `inviteCode` 属于进行中的课堂 | `inviteCode` | 可（最省事） |
| 扫码签到 | `app/scan` 把二维码原文映射成 lessonId | 二维码原文 | 可（转发原文即可） |
| 定位签到 | 会话已开 + 坐标落在 `radiusM` 内 + 时间窗 | 会话 + 一对坐标 | 受限（要会话开） |

四类都不需要教师号、不需要开课、不需要 PC 端。

### 32.2 统一端点与三条材料（模板）

```
# ① lessonId（19 位雪花号）
POST /api/v3/lesson/checkin
{"lessonId":"<LESSON_ID>","source":42,"joinIfNotIn":true}

# ② 邀请码（5 位短码，暗号）
POST /api/v3/lesson/checkin
{"inviteCode":"<CODE>","source":22,"joinIfNotIn":true}

# ③ 二维码原文（app/scan 先解析成 lessonId）
POST /api/v3/app/scan   {"url":"<QR_CONTENT>"}
# → {"code":0,"data":{"flow":"normal","type":"checkin","value":"<LESSON_ID>"}}
```

`source` 不参与校验（§31.4 实测 42/21/22/46 逐字段相同），它只决定老师那份记录上写“从哪个入口进来”。`joinIfNotIn:true` 是“不在班里也让我进”，省掉容易被 `50002 LESSON_UNAUTHORIZED` 拦。

### 32.3 每条材料的现实获取路径

| 材料 | 从哪拿 |
|---|---|
| `lessonId` | ①`GET /api/v3/classroom/on-lesson`（进行中课堂列表，实测可用）②课程学习日志点进课堂记录，URL 末段 ③同学转发的 `/lesson/fullscreen/v3/<id>` ④通知/公众号跳转参数 |
| `inviteCode` | 老师端 `GET /api/v3/lesson/detail` 的 `data.invitation.inviteCode`；课堂上黑板/口头念的 5 位码 |
| 二维码原文 | 微信扫一扫的结果**就是文本**（`http://weixin.qq.com/q/<id>`），不是图片；同学截图后识别出的字符串同样可用 |

**二维码与邀请码都没有 TTL**（§31.5：课后 `app/scan` 仍解析成功，`checkin` 才回 `50004 LESSON_END`）。所以“过期码”不是状态，真正的闸门是 lesson 是否进行中。

### 32.4 定位签到：唯一带地理硬限制的一类

```
GET  /api/v3/lesson/location-checkin/eligibility      # 无参数，服务端按会话解析
     → needLocationSignIn / canSign / reason / mode / timeoutMode
       centerLat / centerLng / radiusM / startMs / endMs / lateAfterMs
       serverTime / signed / wouldBeLate / pastOfficialEnd / locationName
```

- `lat/lng/address` 全部由客户端计算并提交，请求体**没有签名、nonce、设备绑定** → 协议层接受任意坐标，服务端只剩地理围栏这一道。

| 签到来源文案（“通过公众号‘正在上课’提示进入课堂”等） | 请求里的 `source` | 不能；伪造 source 只会写出你没做过的入口 |

## §33 定位签到会话的读写边界与"未结束授课"状态机（2026-11-17 00:00–00:20 实测）

> 全部结论标注 observed / inferred。测试对象仍是自建 tstcourse4 / tstclass（classroom 33843601，course 6063098），role=1。

### 33.1 为什么 lesson 级端点集体回 LESSON_END —— 状态机被找到了（observed）

现象链：
1. 上一节 L1（1820383219510814976）被 `POST /api/v3/lesson/end` 正常结束；随后用 `POST /api/v3/lesson/add` 建了 L2（1820394971807984000），但**没有走"进入课堂"**，直接读 `GET /api/v3/lesson/detail` → `{"code":50004,"msg":"LESSON_END"}`。
2. `GET /api/v3/classroom/on-lesson` 却始终把 L2 列为"进行中"（`onLessonClassrooms[0].lessonId = 1820394971807984000, role=1, openTeacher=true`）；H5 教学日志页也同样显示 L2 为"正在上课"。
3. 在这种状态下 `POST /api/v3/lesson/add` 一律 `50400 BAD_REQUEST`（试过 4 种请求头组合 + 字符串/整数 classroomId，全部 50400）。
4. 在 H5 教学日志页点"开启授课"，弹出确认框：**「您在[tstcourse4-tstclass]中开启的授课还未结束，是否恢复授课？」**（按钮：不恢复 / 恢复）。
5. 点"恢复"后约 6 秒，`GET /api/v3/lesson/detail` 从 50004 变 **200 code=0**，并返回新的 `data.invitation`（qrContent `http://weixin.qq.com/q/027f0yEf7jds11TTVYhGcH`）。

结论（inferred，机制层面已由 4→5 的对照支撑）：
- 服务端为"教师-课堂"维护一个**未结束授课**指针；只要这个指针存在，新开课被拒（50400），而 lesson 级读接口在"当前 App 会话没有重绑到该 lesson"时统一回 50004。
- **"恢复授课"是一条独立的重新绑定路径**，它不在 `lesson/add` 里，也不是 `lesson/checkin`（我们当时用 checkin 试过 → 50400）。它由 H5（web 面会话）触发，客户端原生代码里没有对应调用点。
- 因此"新开一节课"= 先让旧课结束或恢复，再 add；单纯 add 会在有残留课的状态下 50400。

## 35. 授课会话（wake session）：50004 的真正来源与 WS 鉴权语义

本节回答一个卡了很久的问题：为什么 `/api/v3/lesson/*` 一直回 `50004 LESSON_END`，以及 WS 的 `hello` 到底用什么当 `auth`。全部 observed（2026-11-17 02:00–03:00，模拟器 emulator-5556 + 抓包 /tmp/mitm/flows.mitm）。

### 35.1 WS `hello` 的 auth = lessonToken（不是 App 的 authorization）

| 实验 | auth 字段 | 服务端回包 |
|---|---|---|
| App 原生真实帧 | 233 字符 JWT（教师页 `/v/lesson/lesson_user_info` 下发的 `user.user_auth`） | `{"op":"hello","lessonid":...,"isAlive":true,...}` |
| 本工具用 App 的 `authorization` JWT（275 字符） | Bearer 后那段 | `{"op":"hello","message":"authorize failed","isReply":true}` |
| 本工具用 `lessonToken`（231 字符，`/api/v3/lesson/add` 或 `lesson/detail` 返回） | lessonToken | `{"op":"hello","lessonid":...,"isAlive":false/isClone:0,...,"isReply":true}` ← **鉴权通过** |
| 已结束的 lesson + 合法 lessonToken | lessonToken | `{"op":"hello","message":"lesson finished","isReply":true}` |

结论（observed）：
1. WS 握手零鉴权：只要 `Upgrade: websocket` + `User-Agent: Android-pad`（或 Android-mobile）即可 101，不带任何 cookie 也能连上。
2. `hello.auth` 走的是 lesson 维度令牌，App 的会话 JWT 不被接受 → 报 `authorize failed`。
3. `lessonToken` 可通用于同账号下不同 lesson 吗？不能：用 L2 的 token 去 hello 已经结束的 lesson 会直接回 `lesson finished`，说明服务端拿 token 与 lessonid 联合校验。
4. `hello` 回包里 `isAlive` 是「这节课是否处于唤醒（live）状态」的权威位，比 `/api/v3/classroom/on-lesson` 准确。

### 35.2 否定结论：WS 不能把 lesson 变成 live

- `hello` 通过后发 `{"op":"wakelesson","lessonid":...,"title":...,"clone":false,"role":"lecturer"}` → 回 `{"op":"wakelesson","lessonid":...,"isReply":true}`（纯 ack）。
- 紧接着 `GET /api/v3/lesson/location-checkin/session?lesson_id=<同一 id>` → 仍然 `{"code":50004,"msg":"LESSON_END"}`；`POST .../start` → 同样 50004。
- 用 `/tmp/ws_bind.py` 复现三次（不同 lesson、不同 auth）结果一致。**所以「WS 发 hello/wakelesson 就是绑定」这个假设被证伪**。

### 35.3 `/v/lesson/*` 与 `/api/v3/lesson/*` 是两套 lesson 视图

教师端 SPA（`https://fe-static-yuketang.yuketang.cn/fe/static/lesson/3.3.241/js/teacher.6dc0a0e99d18d6e03eaa.js`，724120 字节，本地 /tmp/teacher.js）里端点字典是：

```
reporter:/reporter/collect            lesson_ppt_version:/v/lesson/lesson_ppt_version
lesson_status:/v/lesson/lesson_status lesson_user_info:/v/lesson/lesson_user_info
baseUserInfo:/v/course_meta/user_info remote_control_list:/api/mina/remote_control_list
```

实测（同一 App 会话头）：

| 请求 | 结果 |
|---|---|
| `GET /v/lesson/lesson_status?lesson_id=<刚 add 出来的 id>` | `{"msg":"Lesson matching query does not exist.","status_code":1,"success":false}` |
| `GET /v/lesson/lesson_user_info?lesson_id=<同上>` | 同上 |
| `GET /v/lesson/lesson_user_info?lessonid=<同上>` | `{"msg":"int() argument must be a string or a number, not 'NoneType'"}`（说明它读的是 `lesson_id`） |
| 同上但换成 web 会话 cookie | `{"url":"/login/weixinapp/?next=..."}` → 网页会话已失效 |

即：`/api/v3/lesson/add` 返回的雪花 id 在这套 `/v/` 视图里查不到。两套 id/视图不同源，客户端代码里也没做映射。

### 35.4 50004 的判定条件（当前掌握）

- `POST /api/v3/lesson/add` → `code 0` 且返回 `lessonId` + `lessonToken`，但**只是落了一条记录**；`on-lesson` 立刻能列出来（甚至 lesson 已 end 后仍然列出，属缓存/日报表视图，不可当 live 判据）。
- 对该 id 调 `lesson/detail`、`location-checkin/{session,eligibility,overview,start}` 一律 `50004 LESSON_END`。
- 唯一的反例是 00:21 那次：H5 教师端点了「恢复授课」后，同样的调用立刻变 `code 0` —— 说明**服务端存在一个「唤醒中的授课会话（wake session）」**，只有它存在时 lesson 级接口才开门。
- 没能用客户端手段造出 wake session：App 的「开启授课」在教学日志里有未结束授课时只弹「恢复/不恢复」框；点「恢复」实测发的是 `POST /api/v3/lesson/end {"lesson_id":L2}`（把课结束掉），点「不恢复」进到遥控器页但 flows 里**没有** `lesson/add`（复用残课）。

### 35.5 结论与影响

1. 学生侧所有签到（普通/暗号/扫码/定位）都依赖 live lesson；签到端点本身没有 wake 概念，`/api/v3/lesson/checkin` 在课结束后回 `50004 LESSON_END`、邀请码路径回 `50070 LESSON_END_JOIN`（§31 已实测）。
2. 定位签到的 `wouldBeLate / lateAfterMs / pastOfficialEnd` 只在 wake session 存在时下发；`timeoutMode=2` 的迟到宽限至今**未能实测**（unverified），因为造不出 wake session。
3. 造 wake session 的现实路径只有两条：(a) 网页/PC 教师端「开启授课/恢复授课」；(b) 真实 PC 客户端（PPT 插件）的 wake 流程。App 端不具备该能力。

### 35.6 本轮新增工具

- `tools/ws_client.py`（128 行，py_compile 通过）：裸 socket 实现的 WS 客户端，支持 `hello` / `wake` / `detect` 三种 op，自动从 mitm flows 取 App 会话头（cookie/sessionid/x-uid）用于握手；用于验证 hello 鉴权语义、复现 detectlesson 决策链。

| 7 | `durationSec:120, lateGraceSec:60, timeoutMode:1` | ✓ | 120 s | 120 s | 1 |
| 8 | `startMs/endMs/lateAfterMs` 显式给值（不带 durationSec） | ✗（被忽略） | 300 s（默认） | 300 s | 0 |

`POST /api/v3/location-checkin/update-session` 四次尝试（`{durationSec:600}`、`{durationSec:600,timeoutMode:2}`、`{endMs:…}`、`{startMs,endMs,lateAfterMs,radiusM}`）全部 `{"code":0,"msg":"OK"}`，但 `/session` 的 `endMs`、`lateAfterMs`、`timeoutMode` **一个都没变** → 它改的是「下次开启用的配置」或需要 `sessionId`，对运行中会话无效（参数名 unverified）。

### 36.4 结论

1. `POST /api/v3/lesson/location-checkin/start` 这条路（App/移动 H5 的 mobile-setup 简化版）**只有时长，没有迟到宽限**：`lateAfterMs` 恒等于 `endMs`，`timeoutMode` 只是回显（1=记为迟到 / 2=记为缺勤，来自 `location_sign_config_page.dart` 的 `markAsLate`/`markAsAbsent` 文案），不影响时间窗。
2. 因此在这条路上 `isLate` **永远不可能为 true**：窗口关闭即 `reason=session_ended`（§34.5 已实测 13 点窗口内 + 2 点窗口外）。`isLate` 要出现，必须走 PC/移动 H5 的 `location-checkin/mobile-setup/submit` 路径（带签 setup 链接），而 `mobile-setup/verify` 直接回 `{"code":51218,"msg":"链接无效或已过期"}` —— 该路径本轮仍 **unverified**。
3. 制造 live lesson 的正确姿势不是打接口，而是**用 App 自己的「开启授课 → 恢复授课」**。这对学生侧的意义是：live 状态是服务端按教师端会话设置的，学生端无法自助制造，也无法延长（`extend` 需教师会话）。
4. 教师账号在这节课 per-lesson `role=1`，`location-checkin/submit` 依旧回 `{"code":51210,"msg":"请使用位置签到完成考勤","data":{"success":false}}`（§34.4 复现），所以 `isLate`/`checkInTime` 的写侧依然要靠 role=2 账号。
